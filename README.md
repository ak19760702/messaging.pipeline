# messaging-pipeline

## Предназначение программы

Программа эмулирует обработку потока сообщений из брокера (например TIBCO):

1. сообщения **приходят** со скоростью **t1** (папка `In/` с JSON-файлами);
2. каждое сообщение **обрабатывается** со скоростью **t2**, причём обычно **t2 > t1** (обработка медленнее приёма);
3. результат **отправляется** дальше со скоростью **t1** (папка `Out/`);
4. **порядок** сообщений на выходе должен совпадать с порядком на входе.

### Какую задачу это демонстрирует

Если обработка дольше приёма, один поток не успевает: очередь растёт. Нужно **параллельно разгребать** вход несколькими воркерами. Но параллельная обработка ломает порядок — поэтому результаты собираются в буфер с восстановлением порядка, и наружу уходят строго по очереди.

Программа должна **показать**:

- вход не «захлёбывается» при достаточном числе воркеров (`N ≈ t2/t1`);
- Out идёт в том же порядке, что In;
- в метриках видно загрузку очереди, пула и выходного буфера.

## Архитектура

### Как решается задача

```
In/*.json
    │
    ▼
 FileReader ──sleep(t1)──► очередь ──► пул Worker'ов ──sleep(t2)──┐
 (1 поток, seq)         (bounded)      (N потоков)               │
                                                                  ▼
                                                    ReorderBuffer (кольцо)
                                                                  │
                                                                  ▼
                                                    FileWriter ──sleep(t1)──► Out/
                                                    (1 поток, по порядку)
```

| Механизм | Зачем |
|----------|--------|
| Один Reader + номер `seq` | Зафиксировать порядок прихода |
| Bounded-очередь | Backpressure: не читать бесконечно, если пул не успевает |
| Пул из N воркеров | Разгребать вход, когда t2 > t1 |
| Кольцевой ReorderBuffer | Собрать out-of-order результаты и отдать строго по `seq` |
| Маркер пропуска слота | Если обработка с номером `seq` упала: в буфер кладётся «пусто» вместо данных — файл в Out не пишется, но порядок не зависает на «дыре» |
| Один Writer | Гарантировать порядок записи в Out |

## Обоснование подхода

- **Почему не один поток на всё?** При t2 > t1 входный поток не разгребается — бэклог растёт без предела по времени.
- **Почему пул + reorder, а не «просто несколько потоков в Out»?** Без буфера порядка файлы в Out перемешаются.
- **Почему файлы вместо настоящего брокера?** Так задано в условии: In/Out каталоги эмулируют очереди.

### Почему кольцевой буфер (ring), а не TreeMap

**Фиксированное окно и память.** Размер кольца задаётся конфигом (`app.reorder.window`). Массив слотов выделяется заранее — память **зарезервирована и ограничена**. Нельзя бесконечно копить out-of-order результаты и раздуть heap. У TreeMap размер растёт вместе с «забежавшими вперёд» сообщениями, пока отдельно не введёшь лимит.

**Как устроено кольцо.** Есть массив `slots[window]` и курсор `nextToWrite` — номер следующего `seq`, который разрешено отдать в Out. Слот для сообщения: `index = seq % window`.

**Пропуски (дыры) в кольце.** Воркеры заканчивают работу не по порядку: сообщение с `seq = 5` может лечь в буфер раньше, чем `seq = 3`. Тогда слот для 5 занят (DATA), а слот для 3 ещё EMPTY — «дыра». Writer **не** прыгает к 5: он ждёт именно `nextToWrite` (сначала 3, потом 4, …). Когда опаздывающее сообщение (или маркер пропуска) закрывает дыру — порядок восстанавливается.

**Backpressure.** Worker может положить результат только если  
`seq ∈ [nextToWrite, nextToWrite + window)`.  
Если сообщение «убежало» слишком далеко вперёд (окно ещё не сдвинулось) — `put` **блокируется** (`wait`), пока Writer не продвинет `nextToWrite` и не освободит место в кольце. Так воркеры не забивают память сверх окна.

**Кто и когда забирает следующее сообщение в Out.** Это делает поток **FileWriter** в цикле: вызывает `ReorderBuffer.take()`.

**Condition variable / предикат / wait.** На `ReorderBuffer` висит монитор Java (`synchronized` = мьютекс). Условная переменная — пара `wait()` / `notifyAll()` на том же объекте:

1. Writer в `take()` проверяет предикат: «слот `slots[nextToWrite % window]` уже DATA или маркер пропуска для этого seq?»
2. Если слот пуст (дыра / ещё не готово) и поток не завершён — вызывает **`wait()`** и спит.
3. Когда worker делает `put` / маркер пропуска — **`notifyAll()`**, Writer просыпается, снова проверяет предикат в цикле `while` (классический pattern: ждать, пока условие не станет истинным).
4. После успешного `take` курсор `nextToWrite++`, слот очищается, снова `notifyAll()` — чтобы разбудить воркеров, ждавших сдвига окна.

Итого: следующий для Out — всегда элемент на курсоре `nextToWrite`; «есть ли он?» проверяет Writer через `take()` + wait/notify.

## Настройка программы

Файл: `src/main/resources/application.properties`

| Параметр | По умолчанию | Смысл |
|----------|--------------|--------|
| `app.t1.ms` | 100 | Пауза приёма и отправки (мс) |
| `app.t2.ms` | 300 | Пауза обработки (мс) |
| `app.in.dir` / `app.out.dir` | In / Out | Каталоги |
| `app.queue.capacity` | 100 | Размер очереди (backpressure) |
| `app.reorder.window` | 1000 | Размер кольца reorder |
| `app.workers` | 0 | `0` = авто `ceil(t2/t1)`, иначе явное N |
| `app.write.retry.*` | 3 / 50 | Повторы записи при ошибке IO |
| `app.log.file` | logs/pipeline.log | Базовое имя лога; при старте станет `logs/YYYYMMDDHHMMSS_pipeline.log` |
| `app.metrics.enabled` | true | Сбор метрик |
| `app.metrics.sample.ms` | 50 | Период сэмпла метрик |

### Логирование

Пишется **простым текстом**: каждая строка с префиксом `YYYYMMDDHHMMSS_` (например `20261008200600_Pipeline started...`), в консоль и в файл вида `logs/20261008200600_pipeline.log`.

Лог идёт через `SimpleLog` на пути горячего кода. **На проде подробное логирование каждого сообщения может замедлять систему.**  
Для демо/отладки удобно оставить как есть; если нужно снизить влияние:

- смотреть в основном итоговый summary и блок `--- metrics ---`;
- при необходимости уменьшить объём событий в коде / не гонять лог на каждый seq в нагрузочном режиме.

Метрики отключаются отдельно: `app.metrics.enabled=false` (меньше фоновой работы sampler’а).

## Как запустить и где смотреть результат

**Требования:** Java 17+, Maven 3.9+.

Из корня `messaging-pipeline` (рядом должны быть `In/` и `Out/`):

```powershell
mvn -q -DskipTests package
java -jar target/messaging-pipeline-1.0-SNAPSHOT.jar
```

Или в IntelliJ: Run у `App.main()`, working directory = корень модуля.

**Где результат:**

| Что | Куда смотреть |
|-----|----------------|
| Выходные сообщения | папка `Out/` (`000000.json`, …) |
| Лог работы | консоль Run + `logs/YYYYMMDDHHMMSS_pipeline.log` |
| Метрики | в конце лога блок `--- metrics ---` |
| Успех | процесс сам завершился; summary: назначено ≈ записано + пропуски по маркерам |

В репозитории уже лежит маленький демо-набор: `In/0001.json` … `0004.json` и `bad.json` (для skip).  
Свои файлы — JSON вида `{"id":1,"text":"..."}` с zero-pad именами. Битый JSON seq не получает.

## Что означают метрики

В конце прогона:

| Строка | Смысл |
|--------|--------|
| **In (msg)** | Сколько сообщений лежало во входной очереди (avg / max / p99) |
| **ThreadPool (msg)** | Сколько сообщений сейчас «в руках» у воркеров |
| **Out (msg)** | Сколько результатов ждёт в reorder-буфере до Writer |
| **In rate / Out rate (msg/s)** | Скорость прихода и ухода (avg / max / **p99** по сэмплам) |
| **pool latency (ms)** | Сколько длилась обработка в пуле (≈ t2) |
| **overall** | Средняя скорость за весь прогон и `duration` |

**p99** — значение, ниже которого 99% замеров (типичный «хвост», не единичный max).

Если In почти пустой, ThreadPool ≈ N, а in rate ≈ out rate — пайплайн справляется с приёмом при t2 > t1.

## Возможные улучшения

Если развивать программу дальше:

1. **Периодический вывод метрик** во время работы (сейчас таблица в основном в конце).
2. **Асинхронный / буферизованный лог** или уровни DEBUG/INFO, чтобы на нагрузке не тормозить hot-path.
3. **WatchService** на In/ — не только one-shot batch, а «живой» поток файлов.
4. **Атомарная запись** Out (temp + rename), чтобы не оставлять битый файл при обрыве.
5. **Ограниченный резервуар метрик** (ring/HDR histogram) вместо растущих списков сэмплов.
6. Настоящий брокер (JMS / Kafka) вместо файлов — тот же пайплайн, другие Reader/Writer.
7. Дашборд (JMX / Prometheus) вместо текста в логе.
8. Более гибкая политика при Ctrl+C и fatal IO (уже частично закрыта; можно добавить интеграционные тесты shutdown).

См. также: `docs/architecture.txt` (дизайн), `docs/task.txt` (формулировка задачи).
